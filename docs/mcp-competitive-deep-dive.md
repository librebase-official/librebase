Generated by LibreBaseProjectManagement agent. Database: `librebase_competitive.db`.

## Executive Summary

MCP is no longer a differentiator — it is becoming table stakes. In the last 6 months, 20+ competitors have added some form of MCP. LibreBase's MCP story (hosted endpoint + 15 lifecycle tools + auto-discovery + /for-agents docs) is **genuinely strong** but faces three categories of pressure:

1. **BaaS peers catching up** — Nhost, Directus, Appwrite all added MCP as add-ons
2. **Infrastructure giants leapfrogging** — AWS (15,000 API actions), Supabase (13+ tools + Evals), Neon (12 categories) have deeper, broader MCP surfaces
3. **New entrants built MCP-native** — Harper (schema-driven MCP with RBAC+audit), backenly (agent-driven backend), Knack (HIPAA-compliant MCP)

**Our wedge:** MCP for BaaS entity lifecycle (org/project/instance management), not DB queries or infra control. Auto-discovery + agent docs + KMS trust story + self-host + instance model. But we have a critical gap: **no database-level MCP tools** (query/schema/migrate) — and that is exactly what most agents actually need.

### Tier 2: MCP-Native Architecture (the innovators)

#### Harper — Harper 5.1+ (harper.fast)
| Attribute | Detail |
|---|---|
| **Type** | Native MCP — auto-generates tools from application schema |
| **Architecture** | Two profiles: **Operations profile** (management operations: describe_table, insert, search_by_value, etc.) + **Application profile** (tools auto-generated from HTTP resource handlers — one tool per REST verb per Resource) |
| **Tool generation** | Walks Harper's OPERATION_FUNCTION_MAP, filters through allow/deny lists. Default allow list is intentionally narrow and read-only (describe_*, list_*, search_*, get_*, read_*). get_* is NOT a wildcard — deliberately excludes get_configuration (secrets), get_components (source code), get_backup, get_deployment. |
| **RBAC** | Per-user filtering at tools/list level — each session sees only operations its user can call. super_user sees everything; structure_user sees schema ops; other users see only permission.operations. This is TOOLS/LIST level RBAC — the LLM never even sees tools it can't use. |
| **Annotations** | readOnlyHint (safe to call without confirmation), destructiveHint (prompt before invoking). These are UX hints, not auth — verifyPerms runs at dispatch. |
| **Audit** | Every tool call logged to audit trail. Rate limiting per session (separate read/write limits). Session IDs bound to authenticated user (leaked session can't be reused by different user). |
| **Custom tools** | Resource authors can expose non-verb methods as MCP tools via static mcpTools array — custom name, description, input schema. |
| **Resources** | Exposes harper:// URIs (OpenAPI doc, per-table schema) + https:// URIs (resource descriptors). Schema URIs honor per-user permissions. |
| **Models layer** | Harper 5.1+ has built-in models layer — embedding generation + text generation directly in the DB engine, no external API needed. Harper 5.2 adds more throughput/Node, scheduling, backup, routing. |
| **Getting started** | harper mcp --profile default (stdio transport). harper mcp doctor confirms connection + shows visible tools. |
| **Gartner** | Honorable Mention in 2026 Gartner Magic Quadrant for Cloud-Native Application Platforms |
| **Where we're weak** | Harper's MCP architecture is the most sophisticated in the market — schema-driven, RBAC at tools/list, audit trail, rate limiting, readOnly/destructive hints, custom tool opt-in. This is "MCP done right" for security-conscious agents. Their built-in models layer (embeddings + generation inside DB) is also ahead of us. |
| **How to outplay** | Harper is a DB engine, not a BaaS platform. Their MCP is for managing the Harper instance directly. We are a multi-tenant BaaS with org→instance→project→DB hierarchy. Our MCP manages that hierarchy. Different scope. But we should adopt Harper's best practices: (a) RBAC at tools/list — don't expose tools the agent's user can't use; (b) audit trail on every MCP tool call; (c) rate limiting per MCP session; (d) readOnlyHint/destructiveHint annotations. (e) Add built-in models/embeddings — Harper got there first. |

#### backenly — backenly.com / github.com/backenly
| Attribute | Detail |
|---|---|
| **Type** | Agent-driven autonomous backend platform — Postgres + REST + auth + storage + realtime + functions, driven by coding agent over MCP |
| **Key differentiator** | Governed change kernel — every change is planned, verified, and reversible. This is "infrastructure as code" for backend changes, enforced through MCP |
| **MCP surface** | Agent reads live schema, builds against real tables/auth/storage — not mocks. Connect Claude Code or Cursor over MCP. |

But we should add explicit change governance: plan → verify → apply → revert for instance/project changes via MCP. Our self-host + K8s + licontainer story gives us the infrastructure to implement this. |

## Where We Are Strong

1. **MCP is a first-class feature, not an add-on.** Most competitors added MCP as a side feature (Nhost, Directus, Appwrite) or as infra management (Railway, Render, Fly). Our MCP is core to the platform's agent-first positioning.

2. **Auto-discovery + agent docs.** .well-known/mcp.json + /for-agents + llms.txt. Most competitors require manual npx install + API key config. Our surface is designed for agent consumption from the ground up.

3. **MCP for BaaS entity lifecycle.** Our 15 tools manage orgs, projects, instances, members, hosts, auth providers. This is a different use case from DB query MCP (Supabase, Neon) or infra MCP (Railway, Fly). Agents that need to provision and manage BaaS backends use our MCP.

4. **Self-host + K8s + licontainer.** Harper, Supabase, Neon are hosted-only. For agents in private/regulated environments, our full self-host stack (Docker Compose, K8s Helm, pure-Li licontainer runtime) is a differentiator.

5. **Instance model.** Dedicated (1 inst→1 project) + shared (1 inst→N projects). No competitor offers this. Agents managing multiple isolated instances under one org is our unique architectural niche.

6. **KMS + pure-Li stack.** Cryptographic trust story. Harper has RBAC+audit for MCP security. We have KMS envelope crypto. Combine: "your platform AND your data are verifiable by the agent."

7. **MCP key auth.** Simple MCP key (lb_mcp_...) vs AWS IAM, Supabase OAuth 2.1, Neon API keys. Lower friction for agent onboarding.

## Where We Are Weak

1. **CRITICAL: No database-level MCP tools.** Supabase and Neon expose query, insert, update, delete, list_tables, describe_table, schema_migrate. Our MCP has zero DB tools — only platform lifecycle tools. This is the #1 gap. Agents that connect to our MCP can manage instances but can't query the database inside them. For agents that need to build against a BaaS backend, DB tools are the primary use case.

2. **No evals/benchmarking.** Supabase has an open-source Evals framework that benchmarks AI agents (Claude Code, Codex, OpenCode) building on Supabase. This creates a developer ecosystem around "building agents on Supabase." We have no equivalent. This is a community-building gap, not just a feature gap.

3. **Only 15 tools.** Supabase has 13+, Neon has 12+ categories, AWS has 15,000+ API actions. Our 15 tools are narrowly scoped to platform lifecycle. We need more tools: billing, usage/metering, logs, health, instances (more granular), projects (more granular), orgs (more granular), auth providers (more granular), members, hosts.

4. **No MCP SDK/CLI install experience.** Supabase: `npx @supabase/mcp-server-supabase`. Neon: `neon mcp` CLI. Our MCP is stdio JSON-RPC only — no npm package, no CLI, no one-line install. For developers, our onboarding is harder than competitors.

5. **MCP is not marketed prominently.** Our positioning says MCP is a key differentiator, but the Studio console and landing page don't prominently feature "connect your agent to LibreBase." The /for-agents docs exist but may not be discoverable from the main marketing surface.

6. **No RBAC at tools/list level.** Harper filters tools/list by user permissions — the LLM never sees tools it can't call. We expose all 15 tools to every authenticated MCP session. We should adopt per-user tool filtering.

7. **No audit trail on MCP tool calls.** Harper logs every tool call to an audit trail. We don't. For enterprise/regulated agent deployments, auditability matters.

8. **No rate limiting per MCP session.** Harper has separate read/write rate limits per session. We don't. A runaway agent could hammer our MCP.

## Where We Can Outplay Them

### Short-term wins (now — 1 month)

1. **Document the OpenAI + Anthropic + LangChain + Vercel AI SDK integrations.** These are the top 4 MCP-consuming agent platforms. A clear "Connect your agent to LibreBase" page for each, with copy-paste config, would be a competitive advantage. Most competitors don't have agent-specific docs.

2. **Add run_sql + describe_table + list_tables MCP tools.** This is the single highest-impact gap. It's a small engineering effort (admin-api already has DB access) and immediately puts us in the same category as Supabase/Neon for DB-level MCP. Agents need to query the database — give them the tools.

3. **Publish a "LibreBase MCP for Agents" landing page** at /for-agents (or a dedicated page) that aggregates: auto-discovery info, 15 tool descriptions, copy-paste configs for Claude Desktop/Cursor/VS Code/Cline/OpenAI Agents/LangChain, and a "why LibreBase MCP" pitch. This is our /for-agents surface — make it prominent.

4. **Add MCP tool annotations** (readOnlyHint, destructiveHint) to our 15 tools. This is a small code change that improves agent UX — agents can distinguish safe read operations from destructive writes. Harper does this; we should too.

### Medium-term wins (1–3 months)

5. **Add schema_migrate MCP tool** (Neon's prepare/complete_database_migration pattern). Agents that need to evolve the database schema need a safe migration path. Neon's pattern — create temp branch, apply migration, test, then complete — is the gold standard. Implement the same for LibreBase instances.

## The Real Competitive Dynamic

The MCP market is moving in three waves:

**Wave 1 (2025-2026): MCP as protocol adoption.** Everyone is adding SOME form of MCP. This is where we are. The question is not "do you have MCP" but "what kind of MCP do you have?"

**Wave 2 (2026-2027): MCP as product.** Supabase, Neon, Harper are treating MCP as a product — dedicated docs, tool design, security model, client support. MCP is becoming a competitive axis. The winners will have the best MCP developer experience.

**Wave 3 (2027+): MCP-native platforms.** backenly, Harper (to some extent), Knack are building platforms where MCP is the PRIMARY interface. Agents are the primary users. Human developers use agents that use MCP. This is the agent-first vision we have — but Harper and backenly are executing on it faster than we are.

**Our position:** We are a Wave 1 platform with Wave 2 aspirations and a Wave 3 vision. Our MCP is good (hosted, auto-discoverable, agent-docs) but not yet best-in-class (no DB tools, no eval story, limited tool count, no SDK). The competitors to watch most closely are **Supabase** (most complete BaaS MCP), **Neon** (most comprehensive DB lifecycle MCP), and **Harper** (most sophisticated MCP architecture). They are the ones setting the bar.
